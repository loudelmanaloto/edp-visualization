Unit 1 · Foundations

The Event Loop

In an event-driven program, your code does not decide the order things happen: events do. JavaScript runs one piece of code at a time, and the event loop decides which waiting callback runs next.

Pick a short program and press Load program. Then click Next to watch each line run, or Play to animate it. Before you step, guess the console output, then check your guess.


    

    

  


  

    

      
Parts of the browser event loop

      
Your code runs on the call stack. Slow work (timers, waiting for clicks, network requests) is handed to the browser, which queues a callback when the work is ready. The event loop feeds those callbacks back to the call stack, one at a time.

      

      
    
        
  1. Code on the call stack calls setTimeout, addEventListener or fetch. The browser takes over the waiting, and your code carries on at once.
    2. 
        
  2. When a timer runs out or the user clicks, the browser puts the callback in the task queue.
    3. 
        
  3. When a promise settles (for example a fetch response arrives), its callback goes in the microtask queue.
    4. 
        
  4. Whenever the call stack is empty, the event loop runs every waiting microtask first, then takes the oldest task.
    5. 
      

    

    

    

      
Three ways to organise a program

      

        
ParadigmWho decides what runs next?Typical example

        
          
Imperative (sequential)The program. It runs its statements in a fixed order, top to bottom, and asks for input only when it chooses to.A console program that reads a number with prompt(), computes, prints, and ends.

          
Event-drivenEvents: clicks, key presses, timers, network replies. The program registers handlers and then waits.A web page, a desktop app, a Node.js server. They run until closed.

          
ReactiveData changes. Values are described as streams, and anything that depends on a value updates automatically when it changes.A spreadsheet cell =A1+B1; RxJS observables; signals in Angular, Vue or Solid.

        
      

      
Event-driven programming flips control around. Instead of your code calling the user (“type a number now”), the user’s actions call your code. This is sometimes called inversion of control. Reactive programming builds on events: it treats a series of events as a stream of values you can filter, combine and transform.

    

    

      
How the event loop works

      

        

          
JavaScript in a browser (and in Node.js) runs your code on a single thread. There is one call stack, so only one function runs at any moment. Each callback runs to completion: nothing can interrupt it halfway, not even a click.

          
Slow things never run on that thread. A timer, a click listener or a network request is handed to the browser (the Web APIs), which waits in the background. When the waiting is over, the browser queues your callback.

        

        

          
The rule the demo follows

          
    
            
  1. Run the current task until the call stack is empty.
    2. 
            
  2. Run every microtask, including any new ones added along the way.
    3. 
            
  3. Let the browser repaint the screen if needed.
    4. 
            
  4. Take the oldest task from the task queue and go back to step 1.
    5. 
          

          
Because a task cannot be interrupted, a long loop (like busyWait in the demo) freezes the whole page: no clicks, no timers, no repainting.

        

      

      
setTimeout(fn, 0) does not mean “now”. It means “queue fn as a task as soon as possible”. It still waits for the current code and every microtask to finish, which is why a promise callback beats a 0 ms timer every time.

Callbacks, delegates and function pointers

      
A callback is a function you pass to someone else so they can call it later. Event-driven code is built on them: “when the button is clicked, call this”. Every language has a way to treat a function as a value:

      

        
LanguageHow a function is passed aroundEvent example

        
          
JavaScriptFunctions are values (first-class), including arrow functionsbtn.addEventListener('click', () => save())

          
C#Delegates: typed references to methods; event fields hold a list of thembutton.Click += OnSave;

          
JavaListener interfaces, usually written as lambdasbutton.addActionListener(e -> save());

          
C / C++Function pointers: the address of a functionsignal(SIGINT, on_interrupt);

        
      

      
Callback hell: when each step waits for the previous one through a callback, the code drifts to the right in a deep pyramid. Promises and async/await (see the Async Web tab) flatten it out, but underneath they are still callbacks fed through the microtask queue.

Observer & Pub/Sub

    
The observer pattern lets one object announce “something changed” to any number of listeners without knowing who they are. Pub/sub goes one step further: a broker in the middle delivers messages by topic.

  


  

    

      
Pattern

      

      

      

        
        
        
      

      
      

        
        
        
      

      
Subscribe a few listeners, then press Notify. Try subscribing the same listener twice, or removing a component without cleanup and notifying again.

    

    

      

      

    

    

  


  

    

      
Parts of the observer pattern and pub/sub

      
On the left, the subject holds direct references to its observers. On the right, publishers and subscribers only know the broker and a topic name.

      

    

    

    

      
How the observer pattern works

      

        

          
The subject (also called the observable) keeps a list of functions. Anyone interested calls subscribe(fn) to add their function. When something changes, the subject calls notify(data), which calls every function in the list, in the order they subscribed.

          
The subject never needs to know what the observers do with the data. You can add a new observer (say, a chart) without touching the subject’s code. That is loose coupling.

        

        

          
You already use it

          
    
            
  • button.addEventListener('click', fn): the button is a subject, fn is an observer.
    • 
            
  • Node.js EventEmitter: emitter.on('data', fn) subscribes and emitter.emit('data', x) notifies.
    • 
            
  • Angular / RxJS Observable.subscribe(), and store.subscribe() in Redux.
    • 
          

        

      

    

    

      
Observer vs. publish/subscribe

      

        
ObserverPublish / subscribe

        
          
Who holds the listener list?The subject itselfA separate broker (event bus, message channel)

          
Does the sender know the receivers?It holds references to themNo. It only names a topic

          
FilteringEveryone gets every notificationSubscribers choose topics

          
Where you see itDOM events, EventEmitter, UI componentsMessage brokers (MQTT, Redis pub/sub, Kafka topics), app-wide event buses, WebSocket chat rooms

        
      

    

    

      
Listener leaks and how to avoid them

      

        

          
A subject’s list holds a reference to every subscribed function. A function also keeps alive everything it uses (its closure), often a whole UI component. If a component is removed from the page but never unsubscribes, the garbage collector cannot free it, and its handler keeps running on every notification. Repeat that each time the user opens a screen and memory grows without limit.

          
Two classic bugs: subscribing the same function twice (it runs twice), and unsubscribing with a new arrow function, which never matches, because !== compares references, not code.

        

        

          
Habits that prevent leaks

          
    
            
  • Keep a reference to the handler so you can remove it: const onTick = () => {…}.
    • 
            
  • Pair every subscribe with an unsubscribe in the component’s cleanup (for example ngOnDestroy or a React effect’s cleanup function).
    • 
            
  • Let subscribe return an unsubscribe function, so the caller cannot lose it.
    • 
            
  • Use { once: true } for one-shot listeners, or an AbortController signal to remove many at once.
    • 
            
  • Weak references (WeakMap, WeakRef) do not keep an object alive by themselves, so caches keyed by objects do not leak.
    • 
          

        

      

      
const controller = new AbortController();
window.addEventListener('resize', onResize, { signal: controller.signal });
document.addEventListener('keydown', onKey, { signal: controller.signal });
// when the component is destroyed:
controller.abort();   // removes both listeners at once

Event Queue & Dispatcher

    
Events are not handled the moment they happen. They are put in a queue, and a dispatcher takes them out one at a time and hands each one to the handlers registered for its type.

  


  

    

      

      
      
      
      
      
      
      
Emit a few events (they only join the queue), then press Run dispatcher. addItem triggers a follow-up event. Untick try/catch and include orderPlaced to see one bad handler stop everything.

    

    

      

      

    

    

  


  

    

      
Parts of an event queue and dispatcher

      
Event sources only emit. The queue keeps events in arrival order. The dispatcher loop takes the oldest event, looks up its handlers, and calls them one by one.

      

    

    

    

      
Why queue events at all?

      

        

          
The part of a program that notices an event (a mouse driver, a network socket, a form) and the part that handles it are kept apart. The queue sits between them. Producers add events as fast as they happen; the consumer, the dispatcher, handles them at its own pace and in order.

          
This is the same idea as the browser’s task queue on the Event Loop tab, and the Windows message loop (GetMessage / DispatchMessage) that desktop apps run.

        

        

          
What the dispatcher guarantees

          
    
            
  • Order: events are handled first in, first out.
    • 
            
  • One at a time: a handler runs to completion before the next one starts.
    • 
            
  • Routing: each event goes only to handlers registered for its type.
    • 
            
  • Cascades are safe: a handler that emits a new event adds it to the back of the queue instead of running it immediately, so handlers never nest unexpectedly.
    • 
          

        

      

    

    

      
Custom events

      
You can create and fire your own events, both in the browser and in Node.js. Put your data in the event’s detail (browser) or pass it as an argument (Node.js).

      

        
// Browser: any element (or new EventTarget())
const cart = document.querySelector('#cart');
cart.addEventListener('itemAdded', e => {
  console.log('added', e.detail.name);
});
cart.dispatchEvent(new CustomEvent('itemAdded', {
  detail: { name: 'Mouse', price: 450 },
  bubbles: true
}));

        
// Node.js
const EventEmitter = require('events');
const shop = new EventEmitter();
shop.on('order', (id, total) => {
  console.log('order', id, total);
});
shop.once('order', () => console.log('first!'));
shop.emit('order', 101, 1250);

      

      
Careful: dispatchEvent and emit are synchronous. Every listener runs before the call returns, so code after dispatchEvent(…) runs after the listeners. Only events that come from outside (clicks, timers, network) go through the task queue.

    

    

      
Errors in event and async code

      

        
SituationWhere the error goesHow to handle it

        
          
Plain synchronous codeUp the call stack to the nearest catchtry { … } catch (err) { … }

          
Inside a setTimeout or listener callbackNot to the code that registered it: that code finished long agoPut the try/catch inside the callback

          
A rejected promiseTo the next .catch() in the chain.catch(err => …), or try/catch around await

          
Nobody catches itwindow fires error or unhandledrejection; Node.js may crash the processGlobal handlers for logging, but fix the real cause

          
Node.js error-first callbacksPassed as the first argumentfs.readFile(p, (err, data) => { if (err) … })

        
      

      
The browser protects you a little: if one addEventListener handler throws, the browser reports the error and still calls the other listeners. A home-made dispatcher like the one in the demo does not, unless you add the try/catch yourself.

DOM Event Propagation

    
A click on a button is also a click on everything around it. The event travels down the page to the button (capturing), arrives at it (target), then travels back up (bubbling). Listeners anywhere on that path can react.

  


  

    

      

      

      
      
Each scenario registers different listeners (see the code panel). Press Fire event and step through the three phases. Try clicking the li or ul instead of the button.

    

    

      

      

    

    

  


  

    

      
Parts of event propagation

      
The page is a tree of nested elements. Every event has one target (the element it happened on) and a path from window down to that target.

      

      
Simplified: the real path also includes the html element between document and body.

    

    

    

      
The three phases

      

        

          
    
            
  1. Capturing (eventPhase = 1): from window down to the target’s parent. Only listeners registered with capture: true (or a third argument of true) run here.
    2. 
            
  2. At target (eventPhase = 2): the target’s own listeners run, capturing ones first.
    3. 
            
  3. Bubbling (eventPhase = 3): from the target’s parent back up to window. Ordinary listeners run here. Events like focus, blur, mouseenter and load do not bubble, so this phase is skipped for them.
    4. 
          

        

        

          
target vs. currentTarget

          

            
PropertyMeans

            
              
e.targetWhere the event actually happened. Same at every step.

              
e.currentTargetThe element whose listener is running now. Changes as the event moves.

              
thisSame as currentTarget inside a regular function listener (not an arrow function).

            
          

        

      

    

    

      
Stopping and cancelling

      

        
CallWhat it stopsExample use

        
          
e.stopPropagation()The event moves no further along the path. Other listeners on the same element still run.A click inside a dropdown should not reach the “click outside closes the menu” listener on document.

          
e.stopImmediatePropagation()Everything, at once, including the remaining listeners on the same element.A validation listener that must veto later listeners on the same button.

          
e.preventDefault()Only the browser’s default action (following a link, submitting a form, typing a character). Propagation continues.Handling a form with fetch instead of reloading the page.

        
      

    

    

      
Event delegation

      

        

          
Instead of adding a listener to every li, add one listener to their parent ul. Clicks on any item bubble up to it, and e.target tells you which item was clicked.

          
    
            
  • Works for items added later, with no extra code.
    • 
            
  • One listener instead of hundreds: less memory, nothing to clean up per item.
    • 
            
  • Use e.target.closest('selector'), because the click may land on a child inside the item (an icon or a <span>).
    • 
          

        

        
const list = document.querySelector('#todo');
list.addEventListener('click', e => {
  const del = e.target.closest('button.delete');
  if (!del) return;              // click was elsewhere
  del.closest('li').remove();    // remove that item
});

      

      
Options for addEventListener(type, fn, options): capture (run in the capturing phase), once (remove after the first call), passive (promise not to call preventDefault, which makes scrolling smoother) and signal (remove it with an AbortController).

Debouncing & Throttling

    
Some events fire dozens of times a second: typing, scrolling, resizing. Debouncing and throttling are two small wrappers that decide how often your handler really runs.

  


  

    

      
Technique

      

      

      
      
      
Each number is a moment (in milliseconds) when the user pressed a key. Up to 14 events between 0 and 3000 ms. Run the same events through both techniques and compare the green dots.

    

    

      

      

    

    

  


  

    

      
Parts of a debounced and a throttled stream

      
The same eight key presses, three ways. Shaded boxes are the waiting windows; green dots are the moments the real handler runs.

      

    

    

    

      
Two ways to calm down a noisy event

      

        

          
Debounce: “wait until they stop”

          
Every event cancels the waiting timer and starts a new one. The handler runs only after no event has arrived for the whole wait time. A burst of 50 key presses produces one call, a moment after the last one.

          
Use it when only the final value matters: a search box that calls a server, auto-saving a draft, validating a field, recalculating a layout after the window stops resizing.

        

        

          
Throttle: “at most once every wait ms”

          
The first event runs the handler at once and starts a cooldown. Events during the cooldown are ignored. After the cooldown, the next event gets through. Calls come at a steady, limited rate while the events continue.

          
Use it when you need regular updates during a long burst: scroll position, infinite scrolling, drag and mouse-move tracking, a game’s fire button.

        

      

    

    

      
Side by side

      

        
DebounceThrottle (leading, as in the demo)

        
          
First callOnly after a pause of wait msImmediately

          
During a long, continuous burstNo calls at allAbout one call every wait ms

          
After the burst endsExactly one call, wait ms after the last eventNothing extra (a “trailing” version adds one final call)

          
State it remembersThe pending timerThe time of the last call

          
Built withclearTimeout + setTimeoutDate.now() (or a timer)

        
      

      
Both rely on a closure. debounce(fn, 300) runs once and returns a new function. That function remembers timer (or last) between calls, so the variable survives from one event to the next without being global. Register the returned function: input.addEventListener('input', debounce(search, 300)).

      
For animations tied to scrolling or the mouse, requestAnimationFrame is a built-in throttle: the browser calls your function at most once per screen refresh (about every 16 ms).

GUI Events: a Calculator

    
A graphical app is a set of components (buttons, fields, menus, dialogs) that act as event sources. This calculator is built entirely from event handlers in JavaScript. Click its keys and follow each click from the mouse to the screen.

  


  

    

      

      
      
      
Click a key on the calculator to load that one click as steps. Type it all clears the calculator, runs the whole sequence (digits, + - *, = and C) and shows the steps for its last key.

    

    

      

      

    

    

  


  

    

      
Parts of a GUI event

      
Every interaction in a graphical app follows the same cycle, whether it is a calculator key, a menu item or a dialog’s OK button.

      

    

    

    

      
Components are event sources

Three ways to wire a handler

      

        
StyleCodeNotes

Lambdas (arrow functions) as handlers

          
Arrow functions are the JavaScript equivalent of C# and Java lambdas: short, inline handlers such as btn.addEventListener('click', () => count++). They have no this of their own, so inside them use e.currentTarget to get the element. In a regular function listener, this is the element.

        

        

          
Build it the event-driven way

          
    
            
  1. Keep all data in one state object (the model).
    2. 
            
  2. Write one render() that draws the screen from the state.
    3. 
            
  3. Wire listeners once. Each handler changes the state, then calls render().
    4. 
          

          
The calculator above, a to-do app and a quiz app all follow this shape.

        

      

    

    

      
Desktop apps with JavaScript

      
Electron (used by VS Code, Discord and Slack) and Tauri package a web page as a desktop app. The window is a browser view, so every event on this page works the same way there. Electron adds a main process, which owns windows, menus and the file system, and talks to the page (the renderer process) through IPC events: ipcRenderer.send('save', data) in the page, ipcMain.on('save', handler) in the main process.

      
Same idea, other languages: Java Swing runs listeners on the Event Dispatch Thread; C# WinForms runs a Windows message loop. In both, a long handler freezes the window, just as a long JavaScript task freezes a web page.

    

  







  

    
Unit 4 · Web-Based Event-Driven Programming

    
Async Web: fetch, Node & Express

    
On the web, a request to a server is just another event that finishes later. In the browser, fetch with await waits without freezing the page. On the server, Node.js and Express treat each incoming request as an event that flows through a pipeline of middleware.

  


  

    

      
Side

      

      
      
Pick a scenario and press Run. In the browser view, watch the call stack empty while the request is in flight. In the server view, watch which middleware runs and which is skipped.

    

    

      

      

    

    

  


  

    

      
Parts of an Express middleware pipeline

      
A request passes through middleware in the order it was registered. Each one either passes it on with next(), ends it by sending a response, or reports an error with next(err).

      

    

    

    

      
AJAX and fetch

      

        

          
AJAX (Asynchronous JavaScript and XML) is the idea of talking to a server without reloading the page. It began with XMLHttpRequest and its load and error events; today we use fetch, which returns a promise, usually with JSON instead of XML.

          
await pauses only the async function it is in. The rest of the page keeps handling events, and the function resumes later from the microtask queue when the promise settles.

        

        

          
When does fetch fail?

          

            
What happenedfetch’s promiseres.ok

            
              
200 OK, 201 Createdfulfilstrue

              
404 Not Found, 500 Server Errorstill fulfilsfalse

              
No network, DNS failure, CORS blockedrejects(no response)

            
          

        

      

      
Always check res.ok. A 404 or 500 is a successful HTTP conversation, so fetch does not throw. Your code has to turn a bad status into an error itself, as loadUser does on line 10.

    

    

      
The Node.js event loop

      

        

          
Node.js runs JavaScript on one thread, like the browser, and hands slow work (files, sockets, timers) to the operating system and a small thread pool (libuv). Its event loop goes round in phases, each with its own queue:

          

            
PhaseRuns

            
              
1. timerssetTimeout / setInterval callbacks that are due

              
2. pending callbackssome system-level callbacks deferred from the last round

              
3. pollI/O callbacks (file read done, data on a socket); waits here when idle

              
4. checksetImmediate callbacks

              
5. close callbacks'close' events, e.g. socket.on('close')

            
          

        

        

          
Microtasks in Node

          
After each callback, Node empties two queues before moving on: first every process.nextTick callback, then every promise callback. So in a script:

          
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
console.log('sync');
// sync, nextTick, promise, immediate

          
Inside an I/O callback, setImmediate always runs before setTimeout(fn, 0), because the check phase comes right after poll.

        

      

    

    

      
Express middleware is an event pipeline

      

        
function logger(req, res, next) {
  console.log(req.method, req.url);
  next();                         // pass it on
}
function requireAuth(req, res, next) {
  if (!req.headers.authorization)
    return res.status(401).json({ error: 'Login required' });
  next();
}
function errorHandler(err, req, res, next) {
  res.status(err.status || 500).json({ error: err.message });
}

        

          
Underneath, Node’s http server is an EventEmitter: it emits a 'request' event for every incoming request. Express is the listener, and it runs your middleware functions in registration order.

          
    
            
  • A middleware that neither calls next() nor sends a response leaves the request hanging until the client gives up.
    • 
            
  • Order matters: express.json() must come before routes that read req.body; notFound and the error handler go last.
    • 
          

        

      

    

    

      
WebSockets: events in both directions

      

        

          
HTTP is request → response: the server can only answer. A WebSocket starts as an HTTP request, then upgrades to a connection that stays open, so either side can send a message at any time. Each message arrives as a message event. This suits chat, live scores, multiplayer games and dashboards.

          

            
TechniqueHow updates arrive

            
              
PollingThe client asks every few seconds, mostly for nothing

              
Server-Sent EventsOne-way stream from server to client (EventSource)

              
WebSocketTwo-way messages over one open connection

            
          

        

        
// browser
const ws = new WebSocket('wss://example.com/chat');
ws.addEventListener('open', () => ws.send('hi'));
ws.addEventListener('message', e => show(e.data));
ws.addEventListener('close', () => setStatus('offline'));

// Node.js server (the "ws" package)
wss.on('connection', socket => {
  socket.on('message', msg => {
    wss.clients.forEach(c => c.send(String(msg)));
  });
});
